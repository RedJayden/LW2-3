## 전문가 1 (아키텍처/상태관리) — 소유권 분석과 질문 1·2·3의 답

### 현행 구조가 버그를 낳는 이유: "복제 + 은닉 + 나중 제거" 3중 상태

현행 흐름은 원본의 **사본**을 리피터에 넣고, 원본은 캔버스에 **은닉 상태로 남겨두었다가**, Apply 때 **별도 단계로 제거**한다:

```
[다이얼로그 열림] 원본 clone → repeater.sourceObjects   (사본 1)
                 원본 visible=false + excludeFromExport + 플래그 3종   (은닉 상태)
[옵션 변경마다]  전체 재실행: clone 다시 → 이전 프리뷰 제거 → 새 프리뷰   (비동기 경쟁의 온상)
[Apply]          commitMatrix()가 세션 ID로 원본을 찾아 제거   (찾기 실패 = 누수 = 이중 가공)
[Cancel]         프리뷰 제거 + 원본 가시성 복원
```

같은 도형이 **두 곳에 동시에 존재**(캔버스의 은닉 원본 + 리피터 속 사본)하는 순간부터, 두 상태의 정합성을 지키는 책임이 생긴다. 이 정합성이 비동기 clone(대형 DXF는 수백 ms), 400ms 디바운스, 다이얼로그 이중 트리거와 겹치며 깨진 것이 지금까지의 버그들이다. 지난 세션의 다층 방어(세대 토큰, 세션 불일치 정리, 생성기 최종 가드)는 유효한 안전망이지만, **상태머신 자체가 존재하는 한 방어는 계속 필요하다.**

### 권고: 소유권 이동(move semantics) 모델 — 도형은 항상 정확히 한 곳에만 존재

```
[다이얼로그 열림] 원본을 캔버스에서 떼어(remove) 리피터 안으로 이동 → sourceObjects = [원본 그 자체]
                 (복원용 스냅숏: 원래 left/top/origin/visible 몇 개 값만 저장)
[옵션 변경마다]  clone 없음, 재생성 없음 — xCount/spacing만 in-place 갱신 + updateBoundingBox()
[Apply]          리피터를 확정 플래그로 전환. 원본 제거 단계 자체가 없음(이미 안에 있음)
[Cancel]         리피터 제거 + 원본을 스냅숏 값으로 캔버스에 되돌림
```

- **질문 1 답**: "은닉"은 복제 모델이 이중 표시를 피하려고 만든 개념이다. 이동 모델에서는 원본이 캔버스에서 사라지고 리피터가 그 자리(cell(0,0))에 나타나므로 은닉할 대상이 없다.
- **질문 2 답**: "Apply 시 제거"도 복제 모델의 뒤처리다. 이동 모델에서는 제거할 두 번째 실체가 처음부터 만들어지지 않는다. **이번에 겪은 "원본+매트릭스 이중 생성"류 버그가 구조적으로 불가능해진다.**
- **질문 3 답**: "원본 포함 생성"은 두 해석이 있다.
  - **(가) 원본을 캔버스에 별도 객체로 남기고 매트릭스가 나머지 사본을 추가** — 부적합. 원본과 리피터의 스타일/위치를 항상 동기화해야 하고(원본 색을 바꾸면 셀 9,999개도 바뀌어야 함), 가공 시 두 객체를 병합해야 하며, cell(0,0) 위치에서 이중 표시/이중 가공 위험이 재발한다. 실물 사본 기반 도구(LightBurn 등)에서나 자연스러운 모델이다.
  - **(나) 원본이 매트릭스 안으로 들어가 cell(0,0)의 실체가 됨** — **권고안.** 사용자의 직관("원본이 매트릭스에 포함된다")을 만족하면서 동기화 문제가 없다. AutoCAD 연관 배열(associative array)이 원본을 소비해 배열 객체를 만드는 것과 동일한 개념이다.
- 부수 효과: **clone이 사라지므로** 대형 DXF에서의 프리뷰 지연·비동기 경쟁·세대 토큰의 존재 이유가 거의 소멸한다(안전망은 유지하되 발동할 일이 없어짐). Ungroup(해체)은 기존처럼 셀별 clone-out으로 유지.

## 전문가 2 (렌더링/성능) — 100×100 제약과 질문 4의 답

### 실물 사본 방식은 100×100에서 불가능 (Flyweight 유지가 유일해)

- 100×100 = **10,000셀**. 해마 DXF(세그먼트 수백~수천)를 실물 fabric 객체로 복제하면 수백만 세그먼트 — fabric 캔버스는 수천 객체에서 이미 인터랙션이 불가능해진다. `plan_MatrixGridArray.md`가 실측 근거로 Flyweight(가상 셀 렌더링 + 비트맵 blit + 뷰포트 컬링)를 채택한 이유이며, **이 부분은 교체 대상이 아니다.** 이동 모델은 소유권 계층만 바꾸고 렌더링 구조는 그대로 쓴다.
- 이동 모델이 성능에도 유리한 이유: 현재는 옵션 변경(디바운스 400ms)마다 `generateMatrix` 전체(clone 포함)를 재실행한다. 이동 모델은 편집(Edit) 모드가 이미 쓰는 `updateMatrixInPlace()` 경로(속성만 갱신)를 생성 모드 프리뷰에도 그대로 적용 — **프리뷰가 크기 무관 O(1)** 이 된다.

### 입력 100 초과 차단 — 현황과 보강 지점

- **이미 존재**: 다이얼로그 입력은 `MatrixDialog.handleLocalChange`에서 `Math.min(100, Math.max(1, n))`으로 clamp된다(초과 입력 시 100으로 강제 + 폼 값 되돌림).
- **보강 필요(방어선 2곳)**: ① `MatrixRepeater` 생성자/`set()`에서 xCount/yCount를 1~100으로 클램프(저장 레시피 로드·스토어 직접 설정 등 다이얼로그를 우회하는 진입점 방어), ② 저장 파일 역직렬화(`fromObject`) 시 동일 클램프.

### 100×100 가공 명령 총량 — 물리적 한계 고지

- 렌더링은 Flyweight로 해결되지만, **가공 명령 수는 셀 수 × 소스 복잡도**라는 물리 총량을 피할 수 없다. 점(Dot) 소스 100×100 = 10,000 POINT — 문제없음. 반면 이번 해마 DXF는 4셀에 4,316개 명령 → 100×100이면 **약 1,080만 명령**(메모리 ~수백 MB, 생성 수 분, 가공 수 시간)이다.
- 권고: 생성 직전 **예상 명령 수를 추정해 임계(예: 50만) 초과 시 경고 다이얼로그**("이 매트릭스는 N개 명령을 생성합니다. 계속하시겠습니까?")를 띄운다. 차단이 아니라 고지 — 단순 도형 100×100은 정상 사용례이므로 막지 않는다. (버퍼 분할(이슈 G)이 하드웨어 측은 이미 보호한다.)

## 전문가 3 (QA/공정 안전) — 대안 비교, 이행 계획, 리스크

### 대안 비교

| | A. 현행 복제 모델 + 다층 방어(현재 상태) | **B. 소유권 이동 모델 (권고)** | C. 실물 사본 배열 |
|---|---|---|---|
| 이중 표시/이중 가공 | 방어막으로 억제(상태머신 잔존) | **구조적으로 불가능** | cell(0,0) 원본 병존 문제 |
| 비동기 clone 경쟁 | 세대 토큰으로 억제 | **clone 자체가 없음** | — |
| 프리뷰 반응성 | 옵션 변경마다 재생성 | **O(1) in-place** | 대형에서 불가 |
| 100×100 | 가능(Flyweight) | **가능(Flyweight 동일)** | **불가능** |
| Cancel 복원 | 가시성 복원(플래그 3종) | 스냅숏 몇 값으로 되돌림 | — |
| 구현 비용 | 0 (완료됨) | 중간(useMatrixGenerator/MatrixDialog 개편) | — |
| 잔존 리스크 | 새 경로가 생길 때마다 방어 추가 필요 | Undo/직렬화 접점 검증 필요 | 채택 불가 |

**합의: B 채택.** A는 당장의 실기 검증용으로 유효하나(이미 적용됨), 근본 해법은 B다. C는 100×100 요구와 양립 불가로 기각.

### B 이행 계획 (승인 후, 단계별)

1. **P1 — 생성 모드 이동화**: `generateMatrix()`를 "원본 remove → 정규화(현 qrDecompose 로직 재사용) → sourceObjects로 이동 → 스냅숏 저장 → 리피터 add"로 재작성. 옵션 변경 시 재생성 대신 `updateMatrixInPlace()` 재사용(생성/편집 모드 프리뷰 경로 통일).
2. **P1 — Apply/Cancel 단순화**: Apply = 확정 플래그 전환만. Cancel = 리피터 제거 + 스냅숏 복원. `isMatrixOriginal/isPreviewingOriginal/excludeFromExport` 플래그 3종과 `commitMatrix`의 원본 제거 로직 폐기(생성기 최종 가드는 저비용 안전망으로 존치).
3. **P2 — 클램프 보강**: `MatrixRepeater` 생성자·`fromObject`에 xCount/yCount 1~100 클램프.
4. **P2 — 명령 총량 경고**: 생성 직전 예상 명령 수 추정 + 임계 초과 경고.
5. **검증**: ① 단순/DXF/SVG/Image 각각 생성→Apply→가공(원본 잔존 0, 명령 수 = 셀 수×소스), ② Cancel 복원(위치/스타일/선택 가능성), ③ Undo/Redo(생성 전←→후), ④ 저장/로드 왕복, ⑤ 100×100 도트 매트릭스 프리뷰 인터랙션·가공, ⑥ 101 입력 차단(다이얼로그·로드 경로), ⑦ Ungroup 동작 유지.

### 리스크와 완화

- **Undo/History**: 원본 remove가 히스토리에 얽히면 Undo로 "원본+매트릭스 병존" 상태가 재현될 수 있다 → 프리뷰 세션 동안 히스토리 기록을 보류하고 Apply 시 단일 체크포인트("매트릭스 생성")만 남긴다. Cancel은 체크포인트 없음.
- **직렬화**: sourceObjects 직렬화는 기존 `toObject/fromObject` 경로 그대로(이동된 원본도 동일하게 직렬화됨). 로드 시 클램프만 추가.
- **다중 선택(ActiveSelection) 원본**: 자식들을 각각 remove하여 이동 — 현 qrDecompose 정규화 로직을 그대로 재사용하므로 좌표 회귀 위험 낮음.
- 이행 전까지는 현행 A(다층 방어)가 실기를 보호한다 — **B는 별도 라운드로 진행 권장**(현재 진행 중인 스캐너 완료판정 검증과 분리).

## 적용 완료 (2026-07-21, 승인 후 구현)

### P1 — 생성 모드 이동화 (`useMatrixGenerator.ts`)
- `generateMatrix()` 전면 재작성: **clone 없이** 원본(단일/다중 선택 공통 경로)의 절대 변환을 `qrDecompose`로 캡처 → `canvas.remove()` → 셀 프레임 정규화(origin center, topLeft 기준) → `sourceObjects`로 이동. **동기 함수화**(비동기 clone 소멸) → 세대 토큰(`globalGenerationId`)·`CLONE_PROPS` 폐기.
- **세션 내 재호출은 in-place**: 같은 세션의 프리뷰 리피터가 존재하면 재생성 없이 `updateMatrixInPlace()`로 옵션만 갱신 — 프리뷰가 매트릭스 크기와 무관하게 O(1). `MatrixDialog`는 무수정(기존 호출 시그니처 유지).
- Cancel 복원용 스냅숏 `ISourceRestoreEntry[]`를 리피터 런타임 전용 필드 `__sourceRestore`(직렬화 제외)에 보관.

### P1 — Apply/Cancel 단순화
- `commitMatrix()`: **원본 탐색·제거 단계 삭제**(원본이 이미 내부에 있음). 프리뷰 플래그 해제 + 선택 가능 전환 + `__sourceRestore` 폐기 + `object:modified` 1회 발행(Undo 체크포인트). 구 모델의 은닉 원본(`isMatrixOriginal`)이 과거 세이브/Undo에서 유입되면 정리하는 레거시 안전망만 유지.
- `clearMatrix(Cancel)`: 프리뷰 리피터 제거 + `__sourceRestore` 스냅숏으로 원본을 캔버스에 복귀(절대 변환 복원, 단일 원본이면 재선택). 구 모델 플래그 복원 루프는 레거시 호환용으로 존치.
- 기존 안전망 유지: `ScannerGenerator.getAllObjects`의 `isMatrixOriginal/isPreview` 최종 가드, LayerList의 `isMatrixOriginal` 비노출.

### P2 — 클램프·총량 고지
- `MatrixRepeater.clampCount()`(static) 신설: 생성자에서 xCount/yCount를 1~100으로 강제 — `fromObject`(저장 레시피 로드)가 생성자를 경유하므로 로드 경로도 커버. `updateMatrixInPlace()`에도 동일 클램프. (다이얼로그 입력 clamp는 기존 유지.)
- `SinoGalvoProcessPanel.handleGenerate`: 생성 직전 예상 명령 수를 근사 추정(매트릭스 = 셀 수 × 소스 세그먼트 근사)해 **50만 초과 시 경고 토스트 + 로그**. 차단형 확인 다이얼로그는 공용 confirm UI 인프라 확보 후 후속(계획 대비 조정 — CEF 환경에서 `window.confirm`은 억제 시 가공 전체가 막히는 위험이 있어 비차단 고지를 선택).

### 검증 상태
