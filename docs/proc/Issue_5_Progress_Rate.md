# 5. Scanner 모드 Progress Rate 0% -> 50% 점프 및 멈춤 현상 원인 및 해결 계획 (업데이트됨)

## 1. 원인 파악 (Root Cause Analysis)

사용자께서 보고하신 "가공이 시작되자마자 50%나 80%가 표시되고 멈추는 현상"은 현재 C++ 백엔드의 **Progress 이벤트가 '하드웨어 가공(Marking) 진행률'이 아니라 '명령어 버퍼 생성(Buffering) 진행률'을 반환하고 있기 때문**입니다.

1. **SinoGalvo 및 Scanlab 백엔드의 실행 구조**:
   - PC에서 캔버스의 모든 도형을 USB 보드로 일괄 전송(Buffering)합니다.
   - 이후 `StartMarking()`(혹은 `ExecuteList()`)을 호출하여 보드 스스로 가공을 진행하도록 위임하고 C++은 끝날 때까지 대기(Wait)합니다.
2. **현상의 발생 이유**:
   - 2개의 도형을 그렸다면 내부적으로 명령어 개수가 2개(혹은 극소수)가 됩니다.
   - 백엔드는 버퍼링(명령어 전송) 중일 때 진행률을 계산합니다. 버퍼 전송은 수 밀리초(ms) 만에 순식간에 일어납니다.
   - 첫 번째 도형이 버퍼에 담길 때(인덱스 0), 진행률 0%를 전송합니다.
   - 두 번째 도형(마지막 명령어)이 버퍼에 담길 때(인덱스 1), 진행률 `1 / 2 * 100 = 50%`를 전송합니다. (도형 3개일 경우 `4/5 * 100 = 80%`)
   - 이후 실제 레이저 가공 명령(`StartMarking()`)이 실행되면서 C++ 스레드가 블록킹(대기)됩니다.
   - 즉, 사용자가 화면에서 본 50%나 80%는 **눈 깜짝할 새 끝난 버퍼링 진행률**이며, 실제 가공 중에는 어떠한 진행률도 백엔드에서 업데이트하지 않아 멈춰있는 것처럼 보였던 것입니다.

## 2. 3인의 전문가 분석 (Tree of Thought) 및 전략 수정

### Expert 1: 하드웨어/C++ 엔지니어 (Scanlab / SinoGalvo API 분석)
**의견:** 
- **Scanlab**: `m_rtcDriver->GetStatus(rtcStatus, rtcPos)`를 통해 현재 보드가 실행 중인 명령어 인덱스(`rtcPos`)를 실시간으로 읽어올 수 있습니다. 따라서 C++ 백엔드에서 정확한 하드웨어 진행률을 전송할 수 있습니다.
- **SinoGalvo (JhcLib)**: `GetMarkingState()`는 단순히 `1(Busy)` 또는 `0(Idle)` 상태만 반환합니다. 

### Expert 3: 시스템 아키텍트 (최초 해결책 제시 및 반려)
**최초 의견:** SinoGalvo에서 실제 진행률을 보여주기 위해 "도형(혹은 명령어) 단위로 쪼개어 가공(Chunking)" 하는 방법을 제안했습니다.
**사용자 피드백 반영:** 도형 단위로 끊어 쏠 경우, 하드웨어가 멈추었다 출발하는 동작이 반복되면서 **도형과 도형 사이의 인터벌 대기 시간이 너무 길어지는 치명적인 단점**이 지적되었습니다. 레이저 가공 품질과 속도 저하를 막기 위해 이 방식은 폐기합니다.

### Expert 2: 프론트엔드/UI UX 개발자 (최종 해결책 도출)
**의견:**
SinoGalvo의 경우 하드웨어가 실시간 진행률을 반환하지 않고, 백엔드에서 강제로 끊어 쏘는 것도 불가능하므로, **명령어 버퍼는 한 번에 모두 전송하여 가공 품질과 속도를 유지**하되, UI 상의 진행률(Progress) 표시는 **프론트엔드에서 계산된 '총 가공 궤적 거리'와 '마킹 속도'를 기반으로 한 타이머 페이크(Timer-based estimation) 방식으로 복원**해야 합니다. 
단, Scanlab은 C++ 하드웨어 API를 통해 정확한 진행률 추적이 가능하므로, **"Scanlab은 C++ 실시간 하드웨어 진행률을 사용하고, SinoGalvo는 타이머 기반 예상 진행률을 사용하는 하이브리드 구조"**로 변경합니다.

## 3. 수정 계획 (Implementation Plan)

### [수정 1] 프론트엔드: SinoGalvo 전용 타이머 기반 진행률 복원 (`useProcessMonitor.ts`)
* **[MODIFY] `useProcessMonitor.ts`**:
  - `Scanner` 모드일 때 백엔드 컨트롤러 타입(SinoGalvo 인지 Scanlab 인지)에 따라 진행률 업데이트 방식을 분기합니다.
  - 현재 연결된 장비가 **SinoGalvo일 경우에만**, 기존에 작성되어 있던 `estimatedTotalSeconds` (총 가공 궤적 거리 / FeedRate 로 계산된 예상 시간) 로직을 다시 활성화하여 1초마다 부드럽게 0~100%로 올라가도록 복원합니다.
  - C++ 백엔드에서 날아오는 `__onScannerProgress` 이벤트는 단순히 무시(또는 버퍼링 상태 표시에만 사용)하고, 가공(`running`) 중에는 프론트엔드 타이머가 주도하여 진행률을 올립니다.

### [수정 2] 백엔드: Scanlab 진행률 로직 고도화 (`ScanlabController.cpp`)
* **[MODIFY] `ScanlabController.cpp`**: 
  - Scanlab은 타이머 페이크 방식 대신, `ExecuteList()` 실행 후 진입하는 `do ~ while(rtcStatus != 0)` 대기 루프 안에서 `rtcPos`(실행 중인 리스트 위치)를 주기적으로 읽어옵니다.
  - `progress = (rtcPos / 전체 리스트 길이) * 100` 수식으로 **실제 레이저 가공 하드웨어 진행률**을 계산하여 프론트엔드(`__onScannerProgress`)로 실시간 전송합니다.
